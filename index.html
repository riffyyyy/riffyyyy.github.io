Hollows

A Windows game running on our own engine, written from scratch in C++, right down to the math library (vectors and 3×3 matrices). I was project manager and one of the programmers, and I also took on the UX and design decisions for the team.

What I built:

  • Enemy AI built on finite state machines with A* pathfinding
  • Collectibles and the inventory system
  • A JSON-driven event system, so gameplay events could change without a recompile
▶ watch on YouTube
  1. The problemOur team had no UX or game design (UXGD) student, so nobody owned design. Every decision about levels, pacing and player feel had to come from programmers.
  2. The constraintFive programmers and one artist, one academic year, and an engine we had to build ourselves before we could build the game on top of it.
  3. What we testedWe prototyped enemy movement in a 2D test build, trying A* pathfinding on the level grid to see how enemies chased and navigated around the player.
  4. What failedFinding the best pathfinding for the enemies took far longer than planned. We kept iterating and couldn't land on a setup that was both efficient and fun to play against.
  5. What we changedWe cut the scope. Instead of a large game, we focused on making three levels that were well designed and polished.
  6. What happenedCommunication carried us. With no designer, we talked through every design call as a team, and we shipped a complete three-level game on our own engine.

EduVision

An educational app for identifying and collecting insects. I handle the behind-the-scenes side: a Unity editor tool for entering and checking species data, and an export that packs each species into species.json, a .glb model and audio, so the viewer can load it directly.

I also own the collection save data. Each species is stored once by scientific name (scanning it again just bumps a counter), sorted into 10 insect types and 3 rarities, and a corrupted save file won't wipe your progress.

▶ watch on YouTube
  1. The problemNone of us knew much about insects, and there were few references to tell us how many species to cover or how to group them.
  2. The constraintInsect identification ran through an external API with a limited number of calls per key, inside a school timeline with a cross-disciplinary team.
  3. What we testedWe tested identification on specific insect families first, to check accuracy before widening the scope.
  4. What failedWe kept running out of API calls. Each key ran dry before we could finish the rounds of testing we needed.
  5. What we changedWe set up API keys under several team accounts and spread our testing across them, so testing didn't stall.
  6. What happenedBy keeping communication tight across programmers and designers, we built an app with insect identification, card collection, stickers, gamified progression, a 3D model viewer and "learn more" pages for each species.

As a robotic process automation (RPA) developer intern, I designed and deployed 5 automations across SharePoint, Teams, Planner and FormSG, using SharePoint HTTP requests to connect enterprise apps that didn't talk to each other.

of manual work saved

  1. The problemTeams were spending hours every week on repetitive manual workflows across SharePoint, Teams, Planner and FormSG.
  2. The constraintEverything had to run inside the existing Microsoft 365 setup, and each fix had to work for stakeholders from different teams, not just one.
  3. What I testedI triaged each workflow problem with the stakeholders who owned it, built an automation for it with Power Automate or UiPath, and then ran test bots against it.
  4. What failedOne of my test bots broke an existing workflow that colleagues relied on.
  5. What I changedI worked with the colleagues who owned that workflow to trace what went wrong and fix it.
  6. What happenedFive automations went live, saving about 40 hours of manual work per week.
